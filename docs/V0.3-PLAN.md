# v0.3 plan — Plugin platform and real payments

Branches: `release/v0.3` (SuprHost-UI, from `release/v0.2`), `release/suprhost-v0.3` (backend and
HostMate-UI, from `release/suprhost-v0.2`). Scope is the v0.3 section of `ROADMAP.md`, plus the GST tax
invoice that real payments make necessary.

## What exists today

- Payments: an inline `simulated` check in the booking service, not yet the `IPaymentProvider`
  contract of `ARCHITECTURE.md` §8. The website checkout already understands `requires_action` +
  `redirectUrl`.
- Outbox: `outbox_events` is written for some booking events; nothing reads it.
- Notifications: `INotificationChannel` (v0.2) lives in Application, waiting to move into the plugin host.
- Encryption: an AES-GCM helper (guest ID numbers) to reuse for plugin secrets with its own key.

## Risks

- **Razorpay account**: the host needs a Razorpay account. Test-mode keys are free and enough to build
  and test everything; live keys need Razorpay's KYC.
- **Webhooks need a public URL**: local end-to-end tests of Razorpay webhooks need a tunnel (or
  staging). Automated tests use recorded, signed payloads.
- **Money movement**: refunds are real money in live mode. They run only for a cancellation, for
  exactly the refund the policy computes, once (idempotency key = payment id + cancellation), and are logged.
- **Secrets**: plugin config is encrypted at rest with a new key that must be backed up like
  `DataProtection__IdNumberKey`; secrets are write-only in the API (never returned).
- **Outbound webhooks** are an SSRF and abuse surface: strict URL validation, timeouts, size caps,
  per-tenant rate limits.
- **Hold timing**: guests can take minutes on a UPI app; holds are extended while a payment is open and
  the webhook can still confirm a payment that lands just after expiry if the dates are still free
  (otherwise it is refunded automatically).
