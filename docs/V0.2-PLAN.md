# v0.2 plan — Trust, conversation and pricing

Branches: `release/v0.2` (SuprHost-UI, from `release/v0.1`), `release/suprhost-v0.2` (backend and
HostMate-UI, from `release/suprhost-v0.1`). Scope is the v0.2 section of `ROADMAP.md`.

## What exists today

- Backend: `PropertyReview` (rating, text, booking link, owner response); `CustomPrice` (per-unit
  date-range price); iCal **import** only; no email or notification channel at all.
- Website: test-mode sign-in codes shown on screen; confirmation email promised but not sent.

## Order

Each step ships end to end (backend → BFF → page → PMS where relevant) with tests before the next starts.

| # | Item | Why this order |
|---|---|---|
| 1 | **Notification channel + email** (`INotificationChannel`, one email provider, templates): sign-in codes, booking confirmed (guest + host), cancellation | Closes a v0.1 gap; steps 4, 5, 7 depend on it. Turns off on-screen test codes when a provider is configured |
| 2 | **Quote v2**: seasonal/custom prices (`CustomPrice`), min/max stay per date range, cleaning and extra-guest fees, GST; totals shown on search cards and listing | Price is the core of trust; manage-booking (5) re-quotes with it |
| 3 | **iCal export** per unit (secret URL, host copies it into Airbnb/Booking.com) | Small, removes double-booking risk from direct bookings |
| 4 | **Guest verification before a hold** for guests who aren't signed in (email OTP; phone OTP later with SMS) | Uses step 1. Today booking needs sign-in, so this is mostly the same flow, made faster |
| 5 | **Manage booking** from My trips: cancel per policy (reverses revenue, frees dates), change dates (re-quote, keep if price ≤ paid in simulated mode), receipt/invoice (HTML, printable) | Uses 1 + 2 |
| 6 | **Wishlists + recently viewed** (signed-in: stored in the PMS; recently viewed: local only) | Independent |
| 7 | **Reviews and ratings**: post-stay request email with a one-time link, rating summary on listing and cards, host replies in the PMS, `AggregateRating` in JSON-LD | Uses 1; needs completed stays |
| 8 | **Search v2**: date-range calendar in the search bar, flexible dates (± 1–3 days), "search as I move the map" | Front-end heavy; last so pricing (2) is settled |
| 9 | **Add-to-calendar (.ics) + printable confirmation** | Small; rides on 5's receipt page |
| 10 | **On-site chat relayed to WhatsApp** (Business Cloud API): threads stored against guest/booking, panel + My trips, host replies on WhatsApp | Biggest external dependency; built last, behind a feature flag, so the rest can ship without it |

## Risks

- **WhatsApp Business Cloud API** needs a verified Meta Business account, a dedicated number and
  approved message templates (days to weeks). If not ready, v0.2 ships with the v0.1 hand-off and
  chat moves to v0.2.x.
- **Email deliverability**: needs a sending domain with SPF/DKIM/DMARC. Without it, codes land in spam.
- **Quote v2 touches revenue**: fees and GST must match what the PMS records. Contract tests
  compare quote and recorded revenue line by line.
- **Reviews are public content**: plain text only, length caps, host moderation before publish, and
  only guests with a completed stay can review (one per booking).
- **Cancel/change in simulated payments**: no refunds to move yet; v0.3 adds gateway refunds behind
  the same command.
